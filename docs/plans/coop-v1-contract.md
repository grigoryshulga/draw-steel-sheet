# Контракт первой версии столов

Реализация авторизована пользователем 7 ноября 2026 года. Главный интегратор владеет `src/lib/tables/types.ts`, `src/types.ts`, `package.json`, навигацией, оболочкой и генерируемыми файлами. Делегаты не меняют эти файлы.

Стол постоянный, до десяти участников включая ведущего. Ведущий не добавляет своего героя. У игрока несколько героев, активен один; герой принадлежит одному столу. Общий обзор и открытые разделы доступны всем участникам одинаково. Личные заметки открываются по отдельности. Сцены: бой, переговоры, монтаж; карта во внешнем VTT. Героя редактирует его владелец. Игроки видят только раскрытых противников, их ход, открытые состояния и словесное здоровье; никаких точных чисел выносливости в публичных ответах или журнале.

## API

Типы — `src/lib/tables/types.ts`. Объекты и payload используют camelCase. Команды требуют уникальный `operationId`; повтор не применяет изменение второй раз. Изменения существующего стола передают `expectedRevision`; устаревшая версия возвращает конфликт, не перезаписывает данные.

Supabase RPC: `table_list()`, `table_read(p_table_id text)`, `table_command(p_table_id text, p_command jsonb)`, `table_templates()`, `table_template_save(p_template jsonb)`, `table_template_delete(p_id text)`. В Node локальном режиме аналогичный repository через `/api/tables`, `/api/tables/:id`, `/api/table-command`, `/api/table-templates`. Локальный режим остаётся персональным режимом ведущего; многопользовательские права обеспечиваются Supabase Auth. Клиент явно сообщает это ограничение.

Команды:

- `create`: `{name, memberName}` с null tableId; `join`: `{inviteCode, memberName}` с null tableId.
- `rename`: `{name}`; `rotate-invite`: `{}`; `archive`: `{archived}`; `leave`: `{}`; `kick`: `{userId}`; `allow-member`: `{userId}`; `delete`: `{}`.
- `transfer`: `{userId}` предлагает роль; `accept-transfer`: `{}` принимает, отвязывает героев нового ведущего, предыдущий остаётся игроком.
- `attach-hero`: `{heroId, visibility}` (владелец); `activate-hero`: `{heroId}`; `remove-hero`: `{userId, heroId}` (ведущий); `visibility`: `{heroId, visibility}` (владелец, в том числе в архиве).
- `save-scene`: `{scene}` (ведущий); `delete-scene`: `{sceneId}`; `start-scene`: `{sceneId}` переводит саму сцену в `active`, сохраняя ID и прогресс; копирование — отдельное действие через `save-scene` с новыми ID; `save-material`: `{material}`; `delete-material`: `{materialId}`.
- `event`: `{text, public, kind}`; игрок может публиковать свои сообщения/броски, но не создавать сообщения от чужого имени.
- `offer-item`: `{heroId, toUserId, item, templateId?}`; `answer-offer`: `{offerId, accept, version}`; `revoke-offer`: `{offerId}`.
- `create-trade`: `{toUserId, fromHeroId, toHeroId, offered, requested}`; `confirm-trade`: `{tradeId}`; `cancel-trade`: `{tradeId}`. Сервер проверяет доступное количество и передаёт предметы транзакционно только после двух подтверждений; полученное не экипируется.

Архив запрещает совместные изменения кроме восстановления ведущим, выхода, приватности и действий владельца по удалению стола/передаче. Ожидающие предложения остаются приостановленными. Герои в архиве показываются снимками, но владелец может отзывать доступ. Выход/исключение/удаление героя удаляет снимок и отменяет предложения.

Сигнал синхронизации Supabase содержит только ID стола и номер версии; полное состояние всегда читается авторизованным RPC. При изменении героя обновляется сигнал связанных столов. Все SQL-функции SECURITY DEFINER ограничивают search_path, проверяют auth.uid() и не доступны anon. Таблицы с секретами закрыты прямым SELECT для клиентов.

## Разделение реализации

- Sol xHigh: Supabase таблицы/RPC/права/конкурентность/предметы и локальный серверный адаптер, поведенческие тесты SQL и сервера.
- Terra High: доменные функции сцен и самостоятельные компоненты подготовки/ведения сцен, поведенческие тесты.
- Luna High: небольшая проекция печатных параметров монстров для создания экземпляров, локализованные статусы и тесты.
- Интегратор: общий контракт, repository клиента, стол/участники/предметы, подключение оболочки, офлайн-хранение и интеграция. Следующие задания распределяются после завершения текущих по непересекающимся файлам.

Полный перенос существующих расчётов героя на Go требует отдельной проверки паритета. В первой версии сохраняется совместимый существующий движок героя; границы новых доменных модулей не связывают их с React или хранилищем. Открытый архитектурный выбор Go/WASM не выдаётся за завершённый перенос.
