# Go и WebAssembly для вычислительного ядра

Исследование на 1 ноября 2026 года. Рассматривается стандартный компилятор Go, а не альтернативные реализации. Численные показатели для этого приложения не измерялись. Это сравнение возможностей, а не выбор архитектуры.

## Отправная точка

Приложение использует React и TypeScript; персонажи передаются в JSON (например, `src/lib/persistence/http-repository.ts`), импорт читается в `src/lib/character-import.ts`. Перенос вычислений сам по себе не обеспечивает совместимость: нужен один проверяемый контракт входов, выходов, ошибок и версий данных для существующих сохранений и интерактивных действий.

## Стандартный Go в браузере

Go собирает исполняемый пакет `main` командой `GOOS=js GOARCH=wasm go build -o main.wasm ./cmd/...`. Браузеру также нужен поставляемый с Go `wasm_exec.js`: версия Go 1.N компилятора и файла поддержки должна совпадать. Для Go 1.23 и ранее файл лежит в `misc/wasm`, для более новых — в `lib/wasm`. JS создаёт `new Go()`, передаёт `go.importObject` в `WebAssembly.instantiateStreaming`, затем запускает `go.run(instance)`. Это процесс с runtime Go, а не автоматическое преобразование функций пакета в API TypeScript. Цель `wasip1/wasm` — другой порт для WASI, не прямая замена браузерному `js/wasm`. [Go Wiki: WebAssembly](https://go.dev/wiki/WebAssembly)

Загрузка требует HTTP-ответа для `.wasm` с `Content-Type: application/wasm` при streaming; строгая CSP может запретить компиляцию Wasm. Запрос, компиляция, инициализация и готовность зарегистрированного API — отдельные возможные этапы отказа и задержки. Для не-streaming варианта доступно `fetch` → `arrayBuffer` → `WebAssembly.instantiate`; ошибки загрузки и инициализации нужно обрабатывать явно. [MDN: instantiateStreaming](https://developer.mozilla.org/en-US/docs/WebAssembly/Reference/JavaScript_interface/instantiateStreaming_static), [MDN: загрузка Wasm](https://developer.mozilla.org/en-US/docs/WebAssembly/Guides/Loading_and_running)

### Граница с React

`syscall/js` даёт Go доступ к значениям и вызовам JS; `js.FuncOf` оборачивает Go-функцию для JS, а `Release` освобождает обёртку, когда она больше не нужна. Пакет помечен экспериментальным и исключён из гарантий совместимости Go. Обработчик `FuncOf` при вызове JS приостанавливает event loop; блокирующее ожидание асинхронного JS API внутри него может вызвать deadlock. Для асинхронных операций документация предлагает отдельную goroutine и немедленный возврат обработчика. [Go: syscall/js](https://pkg.go.dev/syscall/js#FuncOf)

Возможный контракт — передавать команды и снимки персонажа через ограниченный адаптер JS/Go и возвращать результат или структурированную ошибку; JSON или JS-объекты требуют явного преобразования. Это вариант для проверки, а не обязательный формат. Жизненный цикл модуля, готовность, отмена устаревших запросов и ошибки должны быть видимы React. При синхронной тяжёлой работе на главном потоке интерфейс может задерживаться; размещение экземпляра в Web Worker позволяет выполнять работу вне потока интерфейса, но Worker не имеет прямого доступа к DOM и общается сообщениями, обычно копируя данные. [MDN: Web Workers](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Using_web_workers)

### Параллелизм

Goroutine и конкурентная структура программы не означают параллельное исполнение Go-кода на нескольких ядрах внутри одного браузерного экземпляра. Исходный код runtime для `js` описывает однопоточную модель; предложение добавить Wasm threads в стандартный Go закрыто как не планируемое. Проверять состояние поддержки следует для конкретной выбранной версии Go. Несколько Workers с отдельными экземплярами — другая схема: отдельное состояние и стоимость запуска и передачи данных, а не автоматически общая куча Go. [Go runtime: lock_js.go](https://go.dev/src/runtime/lock_js.go), [предложение Go #56305](https://github.com/golang/go/issues/56305)

Возможность shared memory в самой платформе WebAssembly не означает, что стандартный Go runtime использует её для параллельных goroutine. Для браузерной общей памяти требуются условия cross-origin isolation; например, COOP `same-origin` и COEP `require-corp` влияют на загрузку внешних ресурсов. Обычный обмен сообщениями с Worker не требует общей памяти. [MDN: изоляция Worker](https://developer.mozilla.org/en-US/docs/Web/API/WorkerGlobalScope/crossOriginIsolated), [MDN: Wasm threads](https://developer.mozilla.org/en-US/docs/WebAssembly/Guides/Understanding_the_text_format#webassembly_threads)

## Серверный Go

Нативный Go-сервис может вызывать то же вычислительное ядро через HTTP: стандартные библиотеки предоставляют [HTTP-сервер](https://pkg.go.dev/net/http#ListenAndServe) и [JSON-кодирование](https://pkg.go.dev/encoding/json). Это даёт общее место выполнения правил для участников стола и возможность серверной проверки действий, но добавляет сетевой путь, эксплуатацию и зависимость интерактивных вычислений от доступности сервиса. Согласование одновременных действий, хранение, авторизация, повтор запросов и разрешение конфликтов не возникают автоматически из Go или HTTP. Другая возможная конфигурация — одно Go-ядро с отдельными адаптерами для сервера и Wasm; совпадение поведения ещё нужно доказать тестами.

Совместимость JSON требует проверки фактических старых файлов: отсутствующие и неизвестные поля, `null`, нулевые значения, числа, строки, расширения и порядок миграций. В частности, стандартный `encoding/json` имеет собственные правила сопоставления и декодирования; его использование не гарантирует эквивалентность текущему TypeScript. [Go: Unmarshal](https://pkg.go.dev/encoding/json#Unmarshal)

## Проверка и собственные замеры

1. Зафиксировать версии Go, браузеров, устройств и набор реальных обезличенных сохранений. До переноса сформировать эталонные примеры результатов текущих правил, включая ошибки и граничные случаи; сравнивать их с Go на native и `js/wasm`, а также проверять чтение и повторное сохранение старых JSON без потери значимых данных.
2. Запускать обычные `go test ./...` для ядра и тесты целевой платформы, например `GOOS=js GOARCH=wasm go test -exec="$(go env GOROOT)/lib/wasm/go_js_wasm_exec" ./...` с установленным Node.js. Node-проверка не заменяет тесты настоящих браузеров, Worker, CSP и развёрнутых заголовков. [Go Wiki: запуск и тестирование](https://go.dev/wiki/WebAssembly#executing-webassembly-with-nodejs)
3. Сравнить существующий TypeScript, Go Wasm на главном потоке и в Worker, а также серверный Go на одинаковых сценариях: загрузка листа, редактирование, массовый пересчёт, действия нескольких игроков. Измерить размеры скачивания до и после сжатия, холодный и повторный старт до готовности, память, время вычисления, сериализации и пересылки, задержку интерфейса и p50/p95/p99 полного действия. Разделить холодный и прогретый запуск, учитывать медленные устройства и сеть; фиксировать число повторов и разброс.
4. Для сервера отдельно измерить сетевой RTT, нагрузку и число одновременных столов, очереди, пропускную способность, стоимость размещения и поведение при отключениях и конфликтах. Для Worker измерить копирование и накладные расходы отдельных экземпляров. Проверить профилирование и доступность диагностики в целевых браузерах.

Ни скорость Wasm относительно JavaScript, ни выигрыш общего Go-ядра, ни приемлемость серверной задержки нельзя вывести из формата исполнения без этих измерений.
