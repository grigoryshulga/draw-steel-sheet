# Серверная часть столов

Контракт: `docs/plans/coop-v1-contract.md`, `src/lib/tables/types.ts`. Миграция не применялась к облаку. Локальный сервер — персональный режим ведущего `userId: "local"`. Supabase Auth и PostgreSQL обеспечивают совместную игру.

## Подключение Node

```js
import { createTablesApi } from './tables-api.mjs';

const handleTablesApi = createTablesApi({
  dataDir: DATA_DIR,
  charactersStore: store, // существующий createStore(DATA_DIR)
});

// До handleApi: существующий API поглощает неизвестные /api/*.
if (await handleTablesApi(req, res)) return;
if (await handleApi(req, res)) return;
```

Точные аргументы `createTablesApi({ store?, charactersStore?, dataDir? })`:

- `store` — готовое **хранилище столов**, реализующее `list/read/command/templates/saveTemplate/deleteTemplate`; при передаче этого аргумента другие аргументы не используются.
- `dataDir` — обязательный каталог при создании встроенного хранилища. Данные пишутся в `path.resolve(dataDir, 'tables.json')`.
- `charactersStore` — существующее хранилище героев с `get(id)`, `save(id, document)`, `list()`. По умолчанию создаётся `createStore(dataDir)`. Встроенное хранилище сохраняет его как `charactersStore`; создание и чтение героев остаётся в существующем `/api/characters`. Второй копии листа нет.

Можно отдельно вызвать `createTablesStore({ dataDir, charactersStore? })` из `server/tables-store.mjs`. `mode` равен `local-director`, `userId` равен `local`. Сервер не принимает пользовательскую идентичность из HTTP, payload или параметров фабрики.

| HTTP | Тело запроса | Ответ |
| --- | --- | --- |
| `GET /api/tables` | — | `{tables: TableSummary[]}` |
| `GET /api/tables/:id` | — | `TableSnapshot` |
| `POST /api/table-command` | `{tableId: string \| null, command: TableCommand}` | `TableSnapshot \| null` |
| `GET /api/table-templates` | — | `{templates: DirectorTemplate[]}` |
| `PUT /api/table-templates` | `DirectorTemplate` | сохранённый `DirectorTemplate` |
| `DELETE /api/table-templates/:id` | — | `{ok: true}` |

Ошибки: `{error: string}`; 400 — некорректные данные, 404 — отсутствующий стол, 409 — конфликт версии/архив, 413 — JSON больше 2 МиБ, 422 — операция совместной игры в локальном режиме. Ответы имеют `Cache-Control: no-store`. Тела команд и исключения не записываются в журнал сервера; неизвестная ошибка возвращается как «Внутренняя ошибка».

Локально реализованы создание/переименование/удаление/архив/восстановление, ротация приглашения, сцены и их копии для проведения, материалы, авторские события, личные заготовки и их версии. `join`, `leave`, `kick`, `allow-member`, `transfer`, `accept-transfer`, команды привязки/активации/видимости героев, предложения и обмен отклоняются с 422. Ведущий не добавляет своего героя; локальный режим не создаёт фиктивных игроков и не пытается атомарно менять несколько файлов героев. Клиент должен явно показывать ограничение локального режима. `subscribe` встроенного хранилища также возвращает ошибку 422; HTTP-клиент может перечитывать данные опросом.

Запись одного JSON включает состояние, заготовки и ключи выполненных операций. Все экземпляры хранилища с одинаковым абсолютным путём сериализуются в одном процессе. Временный файл создаётся с правами 0600, синхронизируется, заменяется `rename`, затем синхронизируется каталог. Повреждённое хранилище вызывает ошибку и не перезаписывается. Запуск нескольких процессов на одном каталоге не поддерживается: это локальная файловая реализация.

## Supabase

Миграция `202611070001_create_tables.sql` требует базовую таблицу `public.characters` из `202610230001_create_characters.sql`. Все RPC принимают camelCase JSON без преобразования на клиенте:

| RPC | Аргументы | Результат |
| --- | --- | --- |
| `table_list()` | — | `TableSummary[]` |
| `table_read(p_table_id text)` | ID стола | `TableSnapshot` |
| `table_command(p_table_id text, p_command jsonb)` | null для `create/join`, иначе ID; команда из контракта | `TableSnapshot \| null` |
| `table_templates()` | — | `DirectorTemplate[]` текущего пользователя |
| `table_template_save(p_template jsonb)` | заготовка с ожидаемой `version` | заготовка с `version + 1` |
| `table_template_delete(p_id text)` | ID собственной заготовки | SQL void |

Новая заготовка передаёт `version: 0`. У существующей передаётся последняя прочитанная версия; тип `scene/item` не меняется. Сцены проверяются и очищаются от неизвестных полей, включая вложенные состояния и счётчики. `start-scene` переводит саму сцену в `active`, сохраняя ID, раунд, ходы, реакции, выносливость и счётчики. Повторный запуск продолжает её. Отдельное копирование через `save-scene` создаёт скрытую подготовку с новыми ID, переназначенным `captainId`, раундом 1, готовыми ходами и свободными реакциями. Для существующей облачной базы требуется миграция `202611070003_start_scene_in_place.sql`.

Все команды требуют `operationId` (ASCII буквы, цифры, `_`, `-`, 1–80 символов). Команды существующего стола требуют `expectedRevision`. Для `create/join` ID стола равен null. Повтор того же ID операции с другим входом конфликтует. Повтор успешной команды возвращает **текущее** авторизованное состояние, а не сохранённый снимок ответа. `leave/delete` и их повторы возвращают null. Если членство отозвано, повтор старой команды не возвращает закрытые данные. Ключи операций не удаляются по TTL.

SQLSTATE `PT409` означает конфликт (HTTP 409), `PT404` — недоступный объект (HTTP 404), `42501` — отказ в правах, `22023` — валидацию. Клиент должен также учитывать транзакционные ошибки `40P01/40001`: откатившуюся операцию можно повторить с прежним ID после перечитывания данных. При изменении `expectedRevision` нужен новый `operationId`, поскольку это уже другой вход.

Изменения сериализуются блокировкой строки стола; создание по одному ID операции — транзакционной advisory-блокировкой. Привязка героя уникальна по `(user_id, hero_id)` для всех столов. До десяти участников, включая ведущего. Исключение блокирует повторный вход этим пользователем до `allow-member`; ротация немедленно отменяет старое приглашение. Передача двухшаговая; принятие отвязывает героев нового ведущего, удаляет их снимки и отменяет связанные предложения/обмены. Предыдущий ведущий остаётся игроком.

## Предметы и конкурентное сохранение героя

`offer-item.heroId` — **герой получателя**, `toUserId` — его владелец. Предмет предлагает ведущий. Заготовка принадлежит отправителю; её текущие эффекты копируются в предложение. Принятие разрешено только получателю, требует точную версию предложения и выполняется вместе с записью предмета в его лист. Отзыв разрешён отправителю. Повтор с прежним ID операции не добавляет предмет снова.

`ItemEffect` — массив до 16 объектов `{field, value}`. Поля: `stamina`, `recoveries`, `speed`, `stability`, `disengage`, `save`, `rolledDamage`, `freeStrikeDamage`; значение — целое от −100 до 100. Объекты с формулами, скриптами или неизвестными полями эффекта отклоняются. Локальный и SQL санитайзеры сохраняют допустимые эффекты.

Изменение эффектов заготовки обновляет только `item.effects` и увеличивает `version` каждого ожидающего предложения, связанного с этой заготовкой. Название, примечания, количество и категория сохраняют исходный снимок. Архивное предложение остаётся приостановленным и тоже получает актуальную версию эффектов; принять его можно после восстановления стола. Изменение только имени/текста заготовки не меняет предложение. Принятые предметы и предложения уже независимы от заготовки. Удаление заготовки оставляет ожидающее предложение с последним снимком.

`create-trade` не является подтверждением. `confirm-trade` нужен от каждого из двух участников; третье лицо не может подтвердить/отменить обмен. Дарение — одна пустая сторона. Сервер проверяет уникальность ID предметов и положительное количество, затем повторно проверяет наличие и количество под блокировками обоих листов при втором подтверждении. В каждой строке `offered/requested` сервер добавляет `item: InventoryItem`: ID, название, примечания, категорию и эффекты только выбранного предмета. `item.qty` равен количеству в условиях обмена, а не размеру всего стека владельца. Эти снимки видят только два участника обмена, в том числе после закрытия их инвентарей; ведущий и третьи лица не получают обмен. Входной `item` игнорируется: снимок всегда формирует сервер. Запрашивать предметы при создании можно только из уже открытого инвентаря другого игрока; полный закрытый инвентарь не читается клиентом. Односторонний дар можно создать из собственного закрытого инвентаря.

Изменение количества, имени, примечаний, эффектов или других полей выбранной строки листа обновляет снимок условий и сбрасывает **все** подтверждения этого обмена. Изменение постороннего предмета или здоровья не сбрасывает их. Удаление выбранной строки, некорректный предмет или нехватка количества отменяет ожидающий обмен. Состояние листов остаётся неизменным до двух новых подтверждений; ошибка во время финальной транзакции откатывает обе записи.

Новые полученные строки имеют новые ID и `equipped: false`. Совпадающие строки объединяются только с неэкипированной строкой, если совпадает всё содержимое кроме ID/количества/отметки экипировки; эффекты тоже участвуют в сравнении. Отсутствующие эффекты и пустой список считаются одинаковыми. При поступлении предмета эффекты не активируются сами.

Предложения/обмены меняют `characters.document.updatedAt` и `characters.updated_at`; триггер обновляет версию стола. **Обязательная интеграционная зависимость:** сохранение листа клиентом должно использовать CAS по `characters.updated_at`, иначе поздняя полная запись может затереть полученные предметы. Интегратор добавляет `202611070002_character_revisions.sql` и RPC `character_save`; тестовый скрипт проверяет совместимость, если этот файл присутствует. Табличная миграция самостоятельно не меняет протокол существующего сохранения героя.

## Приватность, архив и сигналы

Все приватные таблицы находятся в `table_backend` с RLS, без клиентских прав чтения/записи. Прямые таблицы не должны добавляться в exposed schemas PostgREST или публикацию Realtime. `authenticated` получает только доступ к RPC и булевому помощнику членства, нужному RLS сигнала. `anon` не получает доступа. Каждая SECURITY DEFINER функция фиксирует `search_path = pg_catalog`, проверка личности использует `auth.uid()`.

Проекция героя построена из разрешённых полей. Общий обзор доступен всем одинаково; игровые разделы по умолчанию открыты, личные `story/contacts/debts/secrets/misc` закрыты. Открытие игрового раздела включает его авторские примечания к предметам/способностям. Закрытый документ целиком в ответ не попадает.

Игроку передаются только опубликованные сцены проведения и раскрытые существа. Выносливость, максимальная/временная выносливость, численность, БЦ, заметки, ссылки на исходного монстра/капитана, Раздор, закрытые состояния и счётчики отсутствуют в JSON. Заготовки сцен, закрытые материалы и чужие личные события отсутствуют. Автоматического копирования числового состояния в журнал нет; в события попадает только явно публикуемый автором текст. Свободный текст опубликованных описаний/материалов/сообщений не проходит семантическую цензуру: автор намеренно выбирает его публичность. Сервер всегда назначает `actor` сам; игрок может создавать только `message/roll`.

Архив хранит полный снимок привязанных героев в закрытой таблице, включая закрытые разделы. Каждый ответ применяет **актуальные** разрешения владельца. Закрытый и затем открытый раздел показывает состояние на момент архивирования. Восстановление снова использует живой лист; сохранённый архивный документ остаётся приватным и не используется как живое состояние. Следующее архивирование заменяет снимок последним состоянием. Выход, исключение, удаление привязки, удаление героя или аккаунта удаляет соответствующие снимки и отменяет ожидающие предложения/обмены. Архив разрешает восстановление, выход, изменение видимости, удаление стола и передачу роли; совместные игровые изменения отклоняются.

**`public.table_signals` имеет ровно две колонки: `id text`, `revision bigint`.** Фильтр клиента Realtime: `id=eq.<tableId>`, не `table_id=eq.<tableId>`. SELECT сигнала доступен только текущему участнику через RLS. Публикуется только эта таблица. Сигнал содержит только повод перечитать `table_read`, а не снимок или секретные данные. Изменение или удаление привязанного героя обновляет сигнал. Версия монотонна, но одна команда может поднять её несколько раз из-за триггеров; нельзя вычислять её на клиенте прибавлением единицы. Резервный авторизованный опрос нужен для пропущенных событий и проверки отзыва доступа; удалённый участник уже не получит событие, отфильтрованное RLS.

## Проверка

```sh
npx vitest run tests/tables-store.test.ts tests/tables-api.test.ts
scripts/test-tables-sql.sh
git diff --check
```

SQL-скрипт всегда создаёт отдельный `postgres:17-alpine` Docker-контейнер без опубликованных портов и удаляет его при выходе. Он не принимает URL подключения, не читает облачные credentials и не применяет SQL к production. Фикстура моделирует `auth.uid()` и реальные роли `anon/authenticated`; проверяет разных участников, RLS, отсутствие секретов в полном JSON, архив, отзыв доступа, передачу роли, эффекты, версии, атомарность обмена и откат, лимит участников и сигналы. Отдельные подключения соревнуются за одну ревизию и одновременно принимают предложение с одним ID операции.

Полная интеграционная проверка `npm run check` принадлежит интегратору. Эти тесты не устанавливают работоспособность браузера, настоящего Supabase Auth/PostgREST или доставки Realtime. SQL не развёртывался в живом облаке. Используются добавленные интегратором `InventoryItem.effects` и `item?: InventoryItem` в строках `ItemTrade.offered/requested`; других дополнений к общим типам не требуется. Эти файлы серверная реализация не меняет.
