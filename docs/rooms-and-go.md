# Совместная игра и вычислительное ядро

> Рабочий черновик, не утверждённая спецификация. Пожелания игрока выбирать
> открытые разделы и видеть изменения почти сразу уточнены позже; приведённые
> ниже предположения о доступе к заметкам и частоте обновления требуют пересмотра.
> Карта решений находится в `.scratch/sovmestnaya-igra/map.md`.

## Сценарий первой версии

Ведущий создаёт стол и получает ссылку-приглашение. Игрок входит в аккаунт,
переходит по ссылке и выбирает собственного персонажа для стола. Ведущий видит
выбранных персонажей и их сохранённые значения; редактировать лист может только
владелец. Ведущий также может выдать выбранному персонажу заготовленный предмет.
Игрок может убрать своего персонажа из стола и выйти из него.
Предоставление доступа к персонажу должно быть явным: вступление в стол само по
себе не открывает другим участникам всех персонажей игрока.

## Разделение ответственности

- React отвечает за интерфейс и вызывает вычислительное ядро Go через
  WebAssembly. Go рассчитывает правила локально, без сетевого запроса на каждое
  действие. Инициализация ядра асинхронна; интерфейс не должен выполнять
  расчёты до завершения загрузки и должен показывать ошибку при её неудаче.
- Supabase Auth определяет пользователя. Postgres хранит столы, участников,
  приглашения и связи выбранных персонажей со столами. Серверная политика
  доступа остаётся обязательной независимо от проверок в интерфейсе.
- Персонаж остаётся в `characters` у владельца, а стол хранит ссылку на него,
  а не копию. При удалении персонажа или выходе из стола связь удаляется.
  Нельзя идентифицировать персонажа одним `id`: его первичный ключ состоит из
  `user_id` и `id`.
- Ведущий получает только чтение явно опубликованных в его столе персонажей.
  Участникам не предоставляется доступ к другим записям владельца. Содержимое
  листа, включая заметки, может быть видно ведущему: перед публикацией
  интерфейс должен ясно сообщить об этом.
- Ссылка является секретом приглашения: нужен случайный токен с ограниченным
  сроком действия и возможностью отзыва. Вступление доступно только вошедшему
  пользователю; повторный переход не должен создавать дубликат участника.

Для отображения актуального состояния начать с явного обновления и периодического
повторного чтения, отображая время последнего обновления и ошибку сети. Частоту
выбрать после измерения нагрузки. Подписка в реальном времени — отдельное
улучшение, если задержки и нагрузка это оправдают. Доступ к старым данным должен
прекращаться после выхода или удаления из стола.

## Выдача предметов

Ведущий выбирает персонажа, добавленного в его стол, и предмет из существующего
каталога. Выдача относится к конкретной паре владельца и ID персонажа; право
выдавать предметы не даёт ведущему права редактировать остальные поля листа.
Игрок видит ожидающий предмет и подтверждает получение. До подтверждения
инвентарь не меняется. Предложение сохраняется, когда игрок не в сети;
интерфейс показывает состояние выдачи и ошибки доставки.

Текущий автосейв отправляет весь документ персонажа и предполагает одного
писателя. Запись предмета напрямую в `characters.document` может быть затёрта
позднейшим сохранением уже открытого листа. Выдачи следует хранить отдельно
как адресованные операции с уникальным ID, а применение согласовывать с
сохранением персонажа. Повторная доставка или повторный запрос не должны
добавлять предмет дважды; отметка о применении и сохранённое изменение должны
составлять одну атомарную операцию. Для нескольких открытых вкладок и устройств
нужна проверка версии документа или иной механизм разрешения конкурирующих
изменений: простого обновления листа перед сохранением недостаточно.

Сохранение предмета должно использовать существующий формат инвентаря и
устойчивый `catalogId`. При этом следует сохранить текущие правила объединения
количества и обработки титулов; тесты должны проверять повтор операции,
одновременное сохранение игрока, перезагрузку и отсутствие доступа у другого
ведущего. При выходе персонажа из стола ещё не полученные выдачи отменяются;
уже полученные предметы остаются у владельца.

## Совместимость и перенос

Существующий формат документа персонажа и исторические идентификаторы сохраняются.
Go и TypeScript на время миграции сравниваются на одинаковых фикстурах, в том
числе старых сохранениях и пограничных значениях. Для случайных бросков в ядро
передаются конкретные значения кубиков, чтобы расчёт можно было воспроизвести.
Генерация случайных чисел и работа с часами остаются на границе приложения.

При поэтапном переносе каждая механика переключается целиком после проверки
эквивалентности. Нельзя объявлять ядро перенесённым, пока рабочие сценарии
используют старые реализации. Тесты интерфейса, политики доступа и интеграции
остаются необходимыми независимо от языка ядра.

Текущий Supabase-адаптер предполагает, что запросы к `characters` возвращают
только собственные строки: он выбирает их без фильтра пользователя, а загрузка
использует только `id`. Поэтому нельзя просто расширить ему политику SELECT для
ведущего. Доступ к опубликованным персонажам нужно вынести в отдельный,
проверяющий членство запрос или явно ограничить существующие запросы владельцем.
Миграция должна проверяться с несколькими пользователями, совпадающими `id`
персонажей, отозванным приглашением и выходом из стола.

## Порядок работ

1. Зафиксировать контракт ядра, сборку Go/WebAssembly и тесты совместимости;
   перенести правила с сохранением существующего поведения.
2. Добавить модель столов и приглашений, ограничения и проверки доступа на
   стороне базы; проверить их на реальном Postgres с ролями пользователей.
3. Добавить создание стола, вступление по ссылке, выбор персонажа, просмотр
   ведущим и выдачу заготовленных предметов. Проверить обработку выхода, отзыва,
   конкурирующих сохранений и ошибок сети.
4. Измерить время тестов, загрузку WebAssembly и задержку обновления на
   фактических сценариях; оптимизировать найденные узкие места.

Локальное файловое хранилище не предоставляет аккаунтов и прав нескольких
пользователей. Первая совместная версия работает в режиме Supabase; одиночная
работа локального режима сохраняется.

Прототип модели столов сохранён отдельно от миграций в
`.scratch/sovmestnaya-igra/prototype/`. Его можно проверить локально командой
`.scratch/sovmestnaya-igra/prototype/run-rooms.sh`: она запускает временный
Postgres в Docker с тестовой моделью пользователей. Прототип противоречит
согласованным правилам приватности и не готов к развёртыванию; тест не
применяет миграции к облачной базе.
