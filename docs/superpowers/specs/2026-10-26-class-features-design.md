# Модель классовых особенностей: полное покрытие 9 классов

Дата: 2026-10-26 · Ветка: `feat/model-class-abilities`

## Зачем

Лист нельзя использовать как единственный источник истины. Причины, проверенные по данным:

| Что | Сколько |
| --- | --- |
| Атомарных классовых особенностей (уровни 1–10) | **752** |
| Из них спрятаны внутри таблиц и `####`-блоков одного описания | **354** |
| Срабатывают по событию (получаешь урон, конец хода, смежный враг…) | **172** |
| Точек выбора (аспект, орден, домен, традиция, доктрина, коллегия, амплуа) | **206** |
| Бонусов к полям листа (выносливость, скорость, урон, дистанция, толчок…) | **106** |
| Определений и прибавок героического ресурса | **68 + 42** |
| Иммунитетов к состояниям и типам урона | **21** |

Сегодня в модели (`src/data/class-feature-rules.ts`) есть ~30 вариантов выбора у 4 классов из 9, `FeatureEffect` умеет 6 полей, а всё остальное — либо `manualReason` («применяется вручную»), либо свободный текст в `character.classFeatures`, который игрок набирает сам.

Итог: треть арсенала не отображается, числа не сходятся с книгой, о триггерах никто не напоминает.

## Что решено вместе с человеком

1. **Все 9 классов, все уровни 1–10.** Призыватель вне объёма: в данных репозитория у него нет ни фич, ни способностей (пустые статьи 0821–0829), только ресурс и базовые числа в `src/data/classes.ts`. Когда данные появятся — он добавляется по той же схеме.
2. **Глубина способностей — до расчётов.** Структурно: стоимость, ключевые слова, характеристика броска, дистанция, выдача по уровню, применение бонусов урона и дистанции, разблокировка по уровню. Эффекты тиров (`push 2`, `prone`, `slowed (save ends)`) остаются текстом на карточке — как в Forge Steel.
3. **Лист ведёт игрока.** Триггеры отслеживаются состоянием: отметка «использовано» на раунд/схватку, контекст текущего события, сброс по команде. Напоминание — **тихий бейдж в панели особенностей** («сработает: получил урон · 2»), без всплывашек и без отдельного блока, который лезет наверх.
4. **Глубина расчёта — поля листа плюс характеристики.** Считаются: выносливость, восстановления, скорость, устойчивость, отход, спасброски, урон, дистанция. Бонус `+1 к характеристике` из фичи поднимает пороги тиров, потенциал и урон поверх введённого значения, не перетирая его. Иммунитеты к урону и состояниям — показываются с числом, но урон не снижают.
5. **Первый заход — каркас плюс эталонный класс.** Модель, генератор скелета, тест покрытия, панель особенностей и Неистовый целиком. Остальные 8 классов — следующим заходом по той же схеме.

## Как это сделано в Forge Steel (референс)

- Фича — типизированный узел (`Bonus` + `FeatureField`, `CharacteristicBonus`, `Proficiency`, `DamageModifier`, `ConditionImmunity`, `HeroicResource`, `ClassAbilityChoice`, `Choice`, `Multiple`), разложенный по `featuresByLevel`.
- Героический ресурс — **список прибавок с триггером и частотой**: «начало хода, 1d3, раз в раунд», «получаешь урон, 1, раз в раунд», у каждой флаг `used`. На 4/7/10 уровне новая прибавка **заменяет старую по тегу** (`replacesTags`).
- Эффекты тиров способностей — текст с подстановкой характеристики (`"3 + M damage; push 1"`). `push`/`prone` в структуру не разбираются.

Берём модель, не берём код (GPL v3).

## Модель данных

### 1. Скелет (генерируется) и механика (пишется руками)

`scripts/build-class-features.mjs` разбирает `builder.generated.json` (уровень 1) и `level-up.generated.json` (уровни 2–10) и собирает `class-features.generated.json`:

```ts
interface GeneratedClassFeature {
  id: string;            // "fury.aspect.2.inevitable-wrath"
  className: string;
  level: number;
  name: string;
  parentId?: string;     // вложено в таблицу родителя
  keyedBy?: "aspect" | "order" | "domain" | "tradition" | "doctrine" | "college" | "troupe" | "form";
  keyValue?: string;     // "Берсерк", "Домен Солнца"…
  articleId: string;
  featureId?: string;    // id из level-up.generated.json
  description: string;   // markdown, как в книге — для показа
}
```

Всё, что считается и напоминается, живёт отдельно — в авторских файлах `src/data/class-features/mechanics/<class>.ts`, ключом по `id` из скелета. Генерируемый текст остаётся regenerable, авторские числа не перетираются.

### 2. Эффекты (замена нынешнего `FeatureEffect`)

```ts
type FeatureField =
  | "stamina" | "recoveries" | "recoveryValue" | "speed" | "stability" | "save"
  | "disengage" | "rolledDamage" | "freeStrikeDamage" | "distance"
  | "push" | "pull" | "slide" | "potency";

interface FeatureFilter {          // к каким способностям применяется
  keywords?: string[];             // все ключевые слова должны быть у способности
  characteristic?: CharacteristicKey;
  damageType?: string;
  actionType?: ActionType[];
  mode?: "melee" | "ranged";
}

interface FeatureCondition {        // когда эффект действует
  equipment?: { lightArmor?: boolean; lightWeapon?: boolean };
  noKit?: boolean;
  minLevel?: number;
  keyValue?: string[];              // «действует, только если выбран аспект Берсерк»
  resourceAtLeast?: { name: string; value: number };
  formActive?: string;              // Теневая форма, Элементальная форма, Животная форма
}

type FeatureEffect =
  | { kind: "field"; field: FeatureField; value: number; perEchelon?: number;
      perLevel?: number; cap?: number; filter?: FeatureFilter;
      condition?: FeatureCondition; stackingGroup?: string }
  | { kind: "damageImmunity"; types: string[]; value: number | "characteristic";
      characteristic?: CharacteristicKey; condition?: FeatureCondition }
  | { kind: "conditionImmunity"; conditions: string[] }
  | { kind: "characteristic"; key: CharacteristicKey; value: number }
  | { kind: "proficiency"; armor?: string[]; weapons?: string[]; treasures?: boolean };
```

`push`/`pull`/`slide` попадают в расчёт принудительного перемещения способности; `potency` — в бросок потенциала. `stackingGroup` заменяет нынешнее ручное вычитание: в группе побеждает максимальное значение, источник показывается в тултипе.

### 3. Героический ресурс

```ts
interface ResourceGain {
  tag: string;                     // "take-damage"
  event: TriggerEvent;
  amount: string;                  // "1d3", "1", "= Мощь"
  frequency: "round" | "encounter" | "respite" | "always";
  replaces?: string[];             // прибавки, которые отменяются на этом уровне
  used?: boolean;                  // runtime-состояние, не в данных
}

interface HeroicResourceSpec {
  name: string;
  canBeNegative?: boolean;
  gains: ResourceGain[];
  thresholds: { level: number; note: string }[];   // пороги трат: Нуль — 2/4/6/8/10/12
  epic?: { name: string; gains: ResourceGain[] };  // Командование, Уловка, Аплодисменты…
}
```

Прибавки показываются рядом с ресурсом в `ResourcesPanel`: триггер, количество, частота и кнопка «получено» на текущий раунд/схватку.

### 4. Триггеры = напоминания

```ts
type TriggerEvent =
  | "start-of-turn" | "end-of-turn" | "take-damage" | "deal-damage" | "hit" | "crit"
  | "miss" | "ally-damaged" | "adjacent-enemy-damages-you" | "first-per-round"
  | "winded" | "dying" | "spend-recovery" | "enemy-enters" | "save-failed"
  | "save-succeeded" | "respite" | "victory" | "use-ability" | "form-changed" | "passive";

interface FeatureTrigger {
  event: TriggerEvent;
  frequency: "turn" | "round" | "encounter" | "respite" | "always";
  label: string;                   // «получаешь урон» — короткая строка
  detail: string;                  // что делать, из книги
  effect?: FeatureEffect[];        // если часть автоматизируется
  resourceGain?: ResourceGain;
}
```

Контекст события лист знает сам там, где он и так считается:
- «начало/конец хода», «новый раунд», «новая схватка» — кнопки в `SheetQuickActions`;
- «получил урон», «потратил восстановление», «потратил ресурс», «применил способность» — уже идут через `previewGameAction`/`gameHistory` в `src/lib/game-actions.ts`. Журнал действий становится источником контекста.

Всё остальное («смежный враг наносит урон союзнику») игрок отмечает сам одним нажатием на напоминании.

Состояние на персонаже (новое, опциональное — старые листы продолжают работать):

```ts
runtime?: {
  round: number;
  encounter: number;
  triggers: Record<featureId, { round?: number; encounter?: number; count?: number }>;
  forms: string[];                  // активные формы
  resources: Record<string, number>; // дополнительные пулы: благочестие, драма, судьба, пророчество
};
```

### 5. Выборы и уровни

Выборы остаются точками выбора на уровнях 1/2/3/5/8 (и внутри — вложенные варианты). `LevelUpDialog` уже собирает `Record<string, string[]>`. Расширяем: выбор родителя (`aspect`, `tradition`, `domain`) открывает его вложенные фичи и способности; способности фильтруются по стоимости и уровню из `abilityChoices`.

`character.classFeatures` (свободный текст) остаётся, но перестаёт быть местом хранения механики.

## Гарантия полноты

`tests/class-feature-coverage.test.ts`:

1. Каждый `id` из `class-features.generated.json` либо имеет механику в авторских файлах, либо входит в `TEXT_ONLY` с причиной (только проза — например, «вы можете говорить с элементалями»).
2. Каждый `feature.id` из `level-up.generated.json` и каждый `####`-заголовок из `builder.classes[].features` разрешается в скелет — ни одна статья не остаётся без покрытия.
3. Снимок количества фич по классам (77 / 93 / 102 / 75 / 71 / 75 / 88 / 82 / 89) — падение видно в диффе.

Тест падает при появлении новой фичи в данных. Это и есть механизм «ничего не пропадает»: добавили абзац в книгу — сборка красная, пока он не смоделирован или явно не помечен прозой.

## Что меняется на листе

- **`ClassFeaturesPanel`** — все особенности героя по уровням: свёрнутые группы, вложенные варианты выбранного аспекта/домена, тихий бейдж с событием и счётчиком у триггеров, невыбранные варианты видны как «недоступно».
- **`ResourcesPanel`** — прибавки ресурса с триггерами и частотой, отметки «получено», пороги трат по уровню, эпический ресурс.
- **`StatBreakdown`** — в тултипах к выносливости/скорости/устойчивости/отходу/спасброскам назван источник каждого бонуса (частично уже есть).
- **`AbilityCard`** — уже посчитанные бонусы урона и дистанции вписаны в тиры; под карточкой пометка, какие особенности её усиливают.

## Не-цели

- Не структурируем эффекты тиров способностей (толчки, состояния, всплески).
- Не считаем за игрока вероятностные исходы (Молитва проводника «молиться или нет») и переговорные бонусы.
- Не разбираем markdown в механику во время выполнения: только генератор на сборке + авторские данные.
- Призыватель — когда появятся данные.

## Анти-цели

- Механика, записанная прозой в `classFeatures`, — провал.
- «Магический» парсинг описаний ради галочки покрытия — провал: лучше явный `TEXT_ONLY` с причиной.
- Ручной пересчёт там, где число можно вывести, — провал.

## Решения по вопросам ревью

Эти вопросы задал свежий агент-билдер; здесь на них отвечено, чтобы план не начинался с гадания.

- **Старые id выборов не ломаем.** `automation.classFeatureSelections` хранится в листах и в Supabase, `schemaVersion` остаётся 1. В `normalizeCharacter` добавляется одноразовая таблица `старый id → новый id` (30 вариантов, 4 класса) с тестом: ни один сохранённый выбор не теряет бонус. Каноническими считаются id скелета.
- **Выборы не переезжают в level-up.** Фичи 2/5/8 уровня определяются выбором уровня 1 (аспект, орден, домен), поэтому левел-ап их **показывает** как полученные и спрашивает только там, где выбор реальный («выберите 1 из 3 доменных способностей»). Запись — туда же, где сейчас: `automation.classFeatureSelections` + запись в `advancements`.
- **Одна модель эффектов на классы и предков.** `FeatureEffect` расширяется, а не дублируется: 15 записей `ancestry-feature-rules.ts` переводятся на новую форму вместе со своими тестами. Двух параллельных форм в `activeFeatureSources` не будет.
- **Толчки и потенциал — без регэкспов по тексту тиров.** `push`/`pull`/`slide` дают отдельную строку под карточкой способности («толчок: 2 → 3») и не правят текст тира. `potency` сдвигает пороги в `PotencyPanel`, потому что там они и так выводятся из характеристик.
- **Характеристики считаются поверх введённых.** Сохранённое `character.characteristics` не перетирается: эффективное значение = введённое + бонусы фич, и именно оно идёт в `tierThresholds`, потенциал и урон. Пересчёт из `recalculateCharacter` характеристики не трогает — бонус живёт в derived-слое.
- **Иммунитеты — напоминание с числом.** `damageImmunity` и `conditionImmunity` показываются на листе (включая «иммунитет = Разум» конкретным числом) и в бейджах, но не участвуют в `applyDamage`: иначе каждое получение урона требовало бы типа.
- **`runtime` сохраняется вместе с персонажем** (игрок закрывает вкладку посреди схватки), проходит через `previewGameAction` и журнал, поэтому «новый раунд», «новая схватка» и отметки триггеров отменяются как обычные действия. Отмена урона снимает отметку «получил урон».
- **Инвентаризация переезжает в репозиторий** — `docs/superpowers/specs/class-inventory/*.json`, включая списки двусмысленностей по классам. Без неё 8 классов будут решаться вразнобой.
- **Всё видно всегда, числа считаются по флагу.** `ClassFeaturesPanel`, `RemindersPanel` и прибавки ресурса показываются независимо от `automation.enabled`; в расчёт числа идут только при включённом авторасчёте. Существующие тесты на выключенный авторасчёт остаются в силе.

## Что решил я (проверь при чтении)

- Начинаем с эталонного класса **Неистовый**: в нём есть всё — вложенные таблицы аспектов, ресурс с заменами на 4/7/10, триггерные аспекты, бонусы к полям.
- Скелет генерируется, механика пишется руками — иначе 752 фичи не поддерживать.
- Состояние триггеров живёт в `character.runtime` и не требует миграции старых листов.
- Снимок количества фич в тесте — да, хотя он и ломается при каждом обновлении книги; это осознанный сигнал, а не шум.
- Способности берём по уровню и стоимости из существующих `abilityChoices`, не переписывая данные способностей.

## Порядок работ

1. Модель: типы, расширенный движок эффектов (поля, фильтры, условия, группы), derived-слой характеристик, тесты.
2. Генератор скелета + тест покрытия (красный) + перенос инвентаризации в `docs/superpowers/specs/class-inventory/`.
3. Эталон: Неистовый — механики, ресурс с заменами, триггеры, зелёный тест.
4. UI: `ClassFeaturesPanel` с бейджами, прибавки в `ResourcesPanel`, раунд/схватка в журнале действий.
5. **Следующий заход:** остальные 8 классов — параллельно deepseek-агентами по одному классу, каждый закрывается своим покрытием.
6. **Последним:** удаление `class-feature-rules.ts` и `manualReason` вместе с миграцией существующих выборов.

## Риски

- **Двусмысленности в тексте.** В инвентаризации они выписаны списком по классам (кто «цель» у триггеров специализации, порог 8 заменяет 4 у Нуля и т.п.). Каждая спорная — либо явное решение в данных с комментарием, либо `TEXT_ONLY`.
- **Одноимённые фичи на разных уровнях** (Тень: «Улучшение внимательного наблюдения» на 7 и 10). Ключ — `id`, а не имя.
- **Объём.** 752 записи — работа на несколько заходов; эталонный класс и тест покрытия держат качество на каждом шаге.
- **Производительность** панели на 80+ фичах: группы по уровням, ленивый рендер.

## Итог первого захода (реализовано)

Ветка `feat/model-class-abilities`, 25 коммитов, 629 тестов зелёные, `tsc -b` чистый.

Что легло в код: типизированные эффекты и движок полей (`src/data/class-features/types.ts`, `src/lib/feature-modifiers.ts`), эффективные характеристики, генератор скелета (`scripts/build-class-features.mjs`, 844 записи по девяти классам, 476 вложенных), реестр механик с тестом покрытия, активные фичи и триггеры, героический ресурс с заменой по тегу, состояние раунда/схватки с отменой, полное покрытие Неистового (89 записей = 78 механик + 11 `TEXT_ONLY`, 14 триггеров), панель особенностей с бейджами, прибавки ресурса, особенности в левел-апе, строка принудительного перемещения под карточкой способности.

Производительность рендер-пути после кэшей: проход листа способностей 5.9 мс → 0.12 мс.

### Решения, принятые при реализации (с ценой ошибки)

- `rolledOnly?: boolean` остаётся в эффекте поля — без него не сохранить поведение способности без броска с числовым уроном.
- В `ancestry-feature-rules.ts` 11 записей, а не 15: план ошибался, мигрированы все 11.
- `filter.characteristic` и `filter.actionType` удалены как непокрытая выдуманная семантика; `keyValue`, `formActive`, `cap`, `filter.mode` оставлены и покрыты тестами.
- `resolveFeatureAmount({characteristic})` читает сохранённые характеристики: иначе эффективный слой рекурсивно вызывает сам себя. Урон всплеска при этом считается по эффективным.
- `description` родителя в скелете — текст до первого вложенного заголовка; полный текст складывается из родителя и детей.
- Заголовки «Способность …» и строки таблиц доменов входят в скелет: иначе тест покрытия пришлось бы ослаблять исключениями.
- Генератор скелета стоит в `npm run data` **после** `data:rules` (план требовал «до» — это была ошибка).
- Стабы с `description`, начинающимся с `|`, запрещены: ключ проставляется уже разобранной записи.
- `keyValue` фильтрует активацию только при заданном `keyedBy`; пороговые строки таблиц живут по уровню и гейтятся в механике.
- Список активных фич фильтруется статичными условиями (`keyValue`/`minLevel`/`formActive`), а динамический порог ресурса не скрывает строку, а показывает бейджем «нужно N».
- `SELECTION_GROUPS` в этом заходе содержит только Неистового: остальные восемь получат записи вместе с удалением старого реестра, иначе бонусы задублируются.
- Аспект для Неистового пишется **названием** в `fury.aspect`; до появления селекта значение берётся из `character.subclass`.
- Эпический пул ресурса гейтится уровнем (по умолчанию 10); `damageImmunity` получил множитель характеристики ради правила 10-го уровня Неистового.
- Панель показывает только то, что даёт механику, плюс прозу у смоделированных классов; контейнеры не показываются никогда. `NOT_YET` предназначен только для классов с ещё не перенесёнными механиками.
- Иммунитеты в панели идут одним источником (`featureDamageImmunities`), а показ не зависит от `automation.enabled` — расчёт зависит.
- Строка «Толчок +N» под карточкой — эвристика показа по тексту тиров, а не разбор эффектов в структуру.
- Пороги в памятке ресурса выводятся из активных фич (`when.resourceAtLeast`), а не из несуществующего поля `thresholds`.
- Проводник перенесён: все 141 записи скелета распределены между подключёнными механиками и `TEXT_ONLY` с причинами. Ресурс и механики подключены в production wiring, а доменные особенности фильтруются по выбору домена. Автоматизируются только эффекты, выражаемые текущей моделью; прозаические правила остаются подсказками.

### Отложено (minor, для следующего захода)

- Порядок полей в отметках триггеров не канонизирован (`runtimeKey` сортирует только верхний уровень).
- `feature-modifiers.ts` и `class-feature-conditions` стоит разделить: условия живут внутри движка.
- `CLASS_FEATURE_OPTION_NAMES` дублируется в движке; три копии «нулевой» записи характеристик.
- Бейдж порога ресурса на листе и карточка способности считают порог по-разному (показ vs расчёт) — осознанно.
- Выбор аспекта материализует `automation` на старом листе (без последствий, но форма меняется).
- Четыре класса (Цензор, Тактик, Тень, Трубадур) не имеют ни старого реестра, ни механик — раздел особенностей у них пуст до следующего захода.

### Следующий заход

Восемь классов по этой же схеме: `mechanics/<class>.ts` + тест покрытия. Перед параллельным запуском нужны две вещи: расписать `SELECTION_GROUPS` для всех классов одним маленьким заданием и на каждый класс сделать шаг «включить новые данные, вырезать старый реестр, подтвердить, что сумма бонусов не изменилась».

## Второй заход: Цензор (реализовано)

Цензор перенесён целиком: **102 записи скелета = 94 механики + 8 `TEXT_ONLY`** (перки и навыки), `NOT_YET` его больше не содержит. Старого реестра у класса не было, поэтому вырезать и сверять сумму бонусов не пришлось.

Что легло в код:

- `mechanics/censor-base.ts`, `censor-orders.ts` (12 записей орденов), `censor-domains.ts` (36 доменных), `censor-levels.ts` (39 записей 2–10 уровней), `censor-resource.ts` («Гнев» с заменой прибавок на 4/7/10).
- `censor-abilities.ts` — шесть связей «домен → доменная способность»: три карточки 1-го уровня выдаёт билдер, «Благословение тайн» (4) и «Ведомый к Тебе», «Троица Хитрости» (7) выдаёт повышение уровня.
- `SELECTION_GROUPS` для Цензора: `order → censor.order` (значение — название ордена из `character.subclass`) и `domain → censor.domain`; билдер пишет домен в `automation.classFeatureSelections`.
- Тесты чисел и активации: `tests/class-censor.test.ts`.

### Решения, принятые при реализации (с ценой ошибки)

- **Подпись прибавки ресурса живёт в данных.** `ResourceGain.label` добавлен потому, что «первый раз за раунд, когда осуждённый наносит тебе урон» одним `TriggerEvent` не выразить: после замены на 4/7/10 уровнях лист терял контекст и показывал «Наносишь урон». Без поля пришлось бы либо дублировать словарь подписей по `sourceId`, либо врать на листе.
- **Доменная способность — выдача, а не выбор.** У Цензора один домен, поэтому способность его особенности 4/7 приходит вместе с уровнем. Без сохранённого домена повышение на 4/7 честно блокируется с причиной: иначе награда молча терялась бы. В общем тесте повышения фикстура Цензора получила домен — герой без домена невалиден с самого создания.
- **Билдер не предлагает карточки чужих доменов.** Доменная карточка определяется не уровнем, а выбранным доменом: список ручного выбора исключает все имена из `DOMAIN_GRANTED_ABILITIES` для любого класса с доменами (раньше — только Проводник). Одноимённые карточки Цензора и Проводника различаются полем `className`, поэтому герой получает карточку своего класса.
- **Подпись прибавки ресурса из данных главнее специальной ветки движка.** `gain.label` имеет приоритет над `domainGainLabel`; ветка Проводника остаётся запасной для записей без подписи. Ограничение: у 12 доменных прибавок подписи пока зависят от этой ветки. Удаление ветки требует перенести подписи в данные и отдельно проверить паритет.
- **Таблица выборов переехала в `feature-conditions` и ищется по паре «класс + `keyedBy`».** У Цензора две группы; прежний поиск «первая группа этого класса» приписал бы доменным условиям группу ордена.
- **`classFeatureGiftsAtLevel` считает даром любую запись с `keyedBy`, а не только домены Проводника.** Частное исключение удалено: орденские и доменные особенности Цензора описаны прозой, но это реальные награды уровня, и без общего правила они пропадали из плана повышения.
- **Отдых-зависимые бонусы доменов не назначаются автоматически.** «Восстанавливающий ритуал», «Внутренний свет», «Освящённое оружие» и «Улучшенное освящённое оружие» остаются заметками с числом: книга даёт их выбранной цели или выбранному оружию, а лист не хранит ни цель, ни идентификатор предмета. Прецедент — Проводник.
- **Числами моделируются только два домена 7-го уровня.** «Свет палящего солнца» — `+5` к выброшенному урону и иммунитет к огню, равный уровню; «Верхом на молнии» — урон и принудительное перемещение от Присутствия. `+15` по нежити и бонус скорости при активной «Поступи ветра» остаются в заметке: модель не знает тип цели и активные формы. Прибавка «Света палящего солнца» автоматизирована **осознанно вопреки** черновику Проводника с тем же текстом: она постоянная и не зависит от цели. Цена — поле `rolledDamage` не различает тип урона, поэтому иммунитет цели к огню лист не учтёт; это записано в заметке.
- **Способности ордена (2/6/9) и способности «за N гнева» (3/5/8) не потребовали нового кода.** В `level-up.generated.json` уже есть `abilityChoices` с `subclasses` и `abilityIds`; левел-ап спрашивает их существующим общим механизмом, тест это фиксирует.

### Отложено (осознанно)

- «Орудие гнева» и «Улучшенное орудие гнева»: святой урон равен высшей характеристике владельца, спасброски и иммунитет к порче привязаны к выбранному оружию — числа не назначаются.
- Собственные пулы «Видений оракула» (очки судьбы) и «Пророчества» (записанные броски 2d10) — напоминания, в `runtime.resources` не пишутся.
- «Храмовник» и «Добродетель»: портал к божеству, три вопроса, появление в любом мире и приоритетные цели с двойным преимуществом, а также доступ к чужому домену за 3 Добродетели — правила целиком в заметках. Трата и выбор домена остаются за игроком.
- Старый лист Цензора без `character.subclass`: **решено** — выбор ордена в панели теперь синхронизируется с подклассом (`withClassFeatureSelection`), поэтому повышение уровня открывается. То же правило чинит и аспект Неистового.
- Доменные способности 4-го и 7-го уровней (`Благословение тайн`, `Ведомый к Тебе`, `Троица Хитрости`) не приходят из данных повышения: `grantedAbilities` у Цензора пуст. Связь восстановлена вручную в `censor-abilities.ts` по тексту записей; при появлении связи в данных таблицу можно удалить.

### Проверка

`npx tsc -b` чистый, полный набор тестов зелёный (число в дереве меняется вместе с идущей работой Проводника; тесты Цензора — 27). Живые проверки: Цензор 8-го уровня (орден Идеал, домен Война) показывает только свои орденские и доменные особенности, прибавки «Гнева» с подписями событий и замену `+2` на 4-м уровне; повышение 3→4 с доменом Хитрость показывает «Добавятся автоматически: Благословение тайн».

Что легло в код:

  отрицательная полка уже была в `heroicResourceFloor`) и прозаические записи ресурса;
  эпический пул «Видение» на 10-м (`отдых = Опыт`).
- `mechanics/talent-base.ts`, `talent-augmentations.ts`, `talent-sanctuaries.ts`, `talent-early.ts`,

### Решения, принятые при реализации (с ценой ошибки)

- **Старые группы Таланта остаются метаданными выбора.** `talent.augmentation` и `talent.sanctuary`
  сохраняют ID, имена, описания и пишутся билдером как раньше, но их `effects` очищены, а числа живут
  в механиках вложенных записей. Причина: сохранённые листы и Supabase хранят старые ID, а передача
  запрещает удалять используемые группы без замены. Цена: удаление старого реестра целиком откладывается
  до общего финального захода, а `manualReason` у этих опций остаётся служебной строкой.
- **Активация выбора без `keyedBy` — через `when.keyValue` с русским именем опции.** У записей-детей
  аугментаций и оберегов в сгенерированном скелете нет `keyedBy`; генератор не менялся. `selectedKeyValues`
  разворачивает старый ID в имя через `CLASS_FEATURE_OPTION_NAMES`, поэтому старый ID и русское имя
  работают одинаково. Цена: русское имя должно совпадать с названием опции; переименование опции
  потребует синхронной правки механики.
- **Значение чужой группы больше не активирует особенность.** В `selectedKeyValues` добавлена проверка
  владельца опции (ID и уникальное имя), а `keyValueMatches` принимает ровно одно значение. Пара доменов
  Проводника — единственное исключение: она по-прежнему делится по запятой. Без этого оберег, положенный
  в выбор аугментации, включал бы чужую запись.
- **Ресурс — одна спецификация в `CLASS_RESOURCES`.** Базовые прибавки не дублируются в записях
  «Ясность в бою/вне боя»; замены на 4/7/10 уровнях идут через `replaces` по тегам
  (`forced-movement 2`, `start-of-turn 1d3 + 1`, затем `3` и `1d3 + 2`). Обмен Восстановления на 3 Ясности
  в возбужденности — триггер-напоминание, а не прибавка: это выбор игрока.
- **Обереги — триггеры, а не числа.** Скорость/иммунитет/невидимость цели и сроки лист не хранит;
  записи дают точное событие, подпись и подробность, состояние ведёт игрок.
- **Боевая аугментация: два независимых условия.** Лёгкая броня даёт `+3` выносливости за эшелон,
  лёгкое оружие — `+1` к выброшенному урону оружия; оба требуют пустого комплекта. `proficiency`
  показывает владение, но условное владение моделью не выражается — это остаётся заметкой.
  Строка владения теперь читается по-русски (`лёгкая броня, лёгкое оружие, клады`), а не `light, light`.
- **Пси-усиления — заметки без пассивных эффектов.** Семь усилений применяются за трату Ясности по
  выбору игрока; пассивный `field` применял бы их всегда. Числа остаются в тексте и доступны вручную.
- **9-й уровень: иммунитеты показываются, но не уменьшают урон.** `damageImmunity` психического 10 и
  `conditionImmunity` Провокация/Испуг; сопротивление потенциалу через +2 Разума/Интуиции остаётся
  заметкой, потому что модель не считает порог против чужой способности.
- **Способности 8-го уровня не дублируются.** «Поле Левитации» и «Стазисный Щит» уже приходят из
  `grantedAbilities` в `level-up.generated.json`; механики только объясняют запись.
- **Старый лист может выбрать аугментацию и оберег в панели.** `classFeatureChoicesForSheet` теперь
  показывает не-видовые группы из `mechanics.choice` с прежними ID и русскими подписями, а старая панель
  героя скрывает перенесённые группы (`classFeatureLegacyGroupsForSheet`). Иначе на листе было два
  селектора и ложное «По тексту правил».
- **Прозу уровня показывает блок «Что вы получите» только у Таланта.** `classFeatureGiftsAtLevel` добавляет
  ситуативные и характеристические записи в подарки; правило ограничено Талантом, потому что менять
  состав подарков Fury/Censor/Conduit без отдельного ревью нельзя.
- **Видимые `notes` очищены от внутренних имён.** Тест-страж проверяет summary, notes, бейджи и триггеры
  всех выборов Таланта на `light`, `keyValue`, `rolledOnly`, `SUBCLASS_`, `talent.feature.*`,
  `forced-movement` и служебные имена.

### Отложено (осознанно)

- Навык традиции: книга не даёт его вместе с традицией Таланта (в отличие от Нуля); в `notes` записано
  фактическое правило. Классовые навыки Таланта остаются в билдере.
- Смена аугментации/оберега ограничена панелью листа и отдыхом; отдельного валидатора «нельзя взять
  боевую аугментацию с комплектом» в билдере нет — числа просто не применяются, это записано в заметке.
- `kinds: ["resource"]`/`["choice"]` без одноимённого объекта (Ясность, выборы способностей) остаются
  метаданными: панель показывает такую строку как прозу, потому что числа/выбор ведёт другой слой.
- Предсуществующие заметки Цензора и Проводника всё ещё содержат технические имена (`keyedBy`,
  `SUBCLASS_SKILL_SLOTS`, `proficiency`) — это не регрессия Таланта, но следующий заход должен их почистить.

### Проверка

`npx vitest run --testTimeout=60000` — 61 файл, 874 теста зелёные; `npm run build` — чисто, только
предупреждение Vite о крупных чанках; `git diff --check` — чисто. Живой браузерный прогон не выполнялся:
проверка создания/смены/перезагрузки/уровней на реальном листе остаётся ручной.

### Решения, принятые при реализации (с ценой ошибки)

- **Группа `null.augmentation` остаётся метаданными выбора.** Три опции сохраняют ID, имена и описания,
  `effects` очищены, числа живут в механиках с `when.keyValue` по точному русскому имени
  («Аугментация плотности (Density Augmentation)»). Старый ID и имя дают ровно один вклад; чужая группа
  и неизвестное значение не активируют ничего. Цена — та же, что у Таланта: старый реестр удаляется только

- **«Скорость нуля» — характеристика, а не число.** `speed` и `disengage` получают `{characteristic:"agility"}`;
  движок читает сохранённую Ловкость, поэтому изменение характеристики сразу меняет бонус, а сохранённые
  значения листа не перетираются.
- **Таблицы мастерства — строки с двумя условиями.** Каждая строка имеет `when.keyValue` (своя традиция) и
  `when.resourceAtLeast` (порог дисциплины); условие дублируется на эффекте/триггере, иначе число
  применялось бы при любой дисциплине. Строки 12 и порог 2 Метакинетика делят `stackingGroup`, чтобы
  одинаковый бонус к принудительному перемещению не удваивался. Нижние строки 4 и верхние 8 остаются
  отдельными напоминаниями: при 8+ дисциплины в notes прямо сказано отмечать только строку 8 (прецедент Fury).
- **Иммунитет Криокинетика — постоянный эффект, элементное поглощение — нет.** «Энтропийная адаптивность»
  даёт `damageImmunity` к холоду `2×Интуиция`. «Элементальное поглощение» действует только против урона,
  вызвавшего «Инерционный щит», поэтому это триггер с ручным уменьшением, а не постоянный иммунитет.
- **Пси-усиления — заметки.** Семь усилений применяются за трату дисциплины по выбору игрока; пассивные
  поля применяли бы их всегда.
- **9-й уровень даёт только выносливость числом.** «Я и есть оружие» — `+21` выносливости; отсутствие
  кровотечения, старение и подмена Интуиции для сопротивления потенциалам остаются прозой.
- **Прозу уровня показывает блок «Что вы получите» и у Нуля.** `proseGifts` расширены с Таланта на Нуль;
  Fury/Censor/Conduit не менялись.
- **Частичный перенос виден на листе.** `classIsModelled` считает класс начатым, если у него есть
  зарегистрированный ресурс, даже пока `NOT_YET` держит запись ради теста покрытия. Для завершённых классов
  ветка не срабатывает; тест частичного переноса регистрирует ресурс временно и восстанавливает реестр в
  `finally`.
- **Заголовок таблицы 5-го уровня остаётся отдельной строкой.** В скелете у записей 5-го уровня нет
  `parentId`, поэтому контейнер не скрывается как контейнер; его notes прямо называют себя заголовком
  таблицы, а конкретная особенность идёт следующей строкой. Это косметическое ограничение данных скелета,
  а не дубль начисления.

### Отложено (осознанно)

  считаются листом — он не хранит врагов в области и их потенциалы.

  существ остаются ручными.
- Пси-усиления и их числа — напоминания, не пассивные эффекты.
- «Порядок» тратится как дисциплина и даёт +1 к размеру Поля нуля за 1 очко на старте боя — это ручная трата;
  в `runtime.resources` пул не пишется.

## Пятый заход: Тактик (реализовано)

Тактик перенесён целиком: **75 записей скелета = 67 механик + 8 `TEXT_ONLY`** (перки и навыки),
`NOT_YET` его больше не содержит. Старого реестра у класса не было, поэтому миграция не потребовалась;
проверялись ресурс, доктрины, два комплекта и большое количество ситуативных правил.

Что легло в код:

- `mechanics/tactician-resource.ts` — «Фокус» (старт боя `= Победы`, начало хода `2`, урон по отмеченному `1`,
  союзник в 10 клетках использует героическую `1`) и эпический пул «Командование».
- `mechanics/tactician-base.ts` (уровень 1), `tactician-doctrines.ts` (21 keyed-запись 1/2/5/7/8 и 9
  контейнеров способностей 2/6/9), `tactician-levels.ts` (3–10, ресурсные замены 4/7/10).
- `tests/class-tactician.test.ts`.

### Решения, принятые при реализации (с ценой ошибки)

- **Фокус — одна спецификация в `CLASS_RESOURCES`.** Записи «Фокус в бою/вне боя» своих `gains` не имеют;
  замены на 4/7/10 идут через `replaces` по тегам (`marked-damage 2`, `start-of-turn 3`, затем `4`).
  Цена ошибки при дублировании — двойное начисление, поэтому это закрыто тестом на одну строку на тег.
- **Доктрина — подкласс и группа выбора `tactician.doctrine`.** Значение пишется в `character.subclass`,
  keyed-записи 1/2/5/7/8 активируются по названию, контейнеры способностей 2/6/9 получают `when.keyValue`.
  Пустое/неизвестное/составное значение (`"Воевода, Авангард"`) не активирует ни одной записи.
- **Ограничение общего level-up.** Для составного подкласса план повышения может показать способности
  обеих доктрин — это поведение `subclassTokens`/`appliesToSubclass` у всех классов, а не Тактика.
  Лист при этом не активирует ни одну доктрину; выбор в панели заменяет значение на одну известную.
  Исправление общего движка вынесено из этого захода.
- **Два комплекта не дублируются в механике.** «Полевой арсенал» не имеет `effects`: бонусы комплектов уже
  считает существующий слой листа по `character.kit` и `secondaryKit` (максимум по двум, а не сумма).
  Цена — конфликт одинаковых бонусов и выбор «одного из двух» остаются ручными и записаны в notes.
- **Метка — состояние, а не поле листа.** «Кто отмечен», лимит 1→2 и четыре варианта траты 1 фокуса ведутся
  вручную; механика даёт точную формулировку преимущества (герой и союзники в линии воздействия получают
  преимущество на броски силы **против** отмеченного), а не перевёрнутое правило.
- **Прозу уровня показывает блок «Что вы получите» и у Тактика.** `proseGifts` расширены на третий класс;
  Fury/Censor/Conduit не менялись.
- **Ситуативные правила не выдумывают числа.** Приказы, преимущества метки, доктринные проекты, захват
  инициативы, мастерство оружия, «Командование» и «Мастер войны» остаются заметками с точным условием.

### Отложено (осознанно)

- Метка: кто отмечен, лимит и выбор одной из четырёх выгод — состояние способности.
- «Преимущества метки» в способностях 2/6/9 и трата Командования на тир броска — правила карточек.
- Два комплекта: выбор при одинаковых бонусах фиксируется игроком до отдыха, лист это не хранит.
- Составной подкласс в плане повышения — общее ограничение движка, отдельная задача.

## Шестой заход: Элементалист (реализовано)

Элементалист перенесён целиком: **91 запись скелета = 83 механики + 8 `TEXT_ONLY`** (перки и навыки),
`NOT_YET` его больше не содержит. Инвентарь содержит 89 записей: «Эссенция в бою», «Эссенция вне боя» и
«Героические способности» свёрнуты в родителей, зато есть строка «Навыки», которой в скелете нет; счёт идёт
по скелету. Это последний класс со старым реестром — обе группы мигрированы.

Что легло в код:

- `mechanics/elementalist-resource.ts` — «Эссенция» (старт боя `= Победы`, начало хода `2`, урон в 10 клетках
  `1` кроме нетипового/святого) и эпическое «Веяние» (1 веяние → 3 эссенции, ручная трата).
- `elementalist-base.ts`, `elementalist-enchantments.ts`, `elementalist-sanctuaries.ts`,
  `elementalist-early.ts`, `elementalist-specializations-late.ts`, `elementalist-late.ts`.
- `tests/class-elementalist-base.test.ts`, `class-elementalist-levels.test.ts`, `class-elementalist-ui.test.ts`.

### Решения, принятые при реализации (с ценой ошибки)

- **Старые группы `elementalist.enchantment`/`sanctuary` остаются метаданными выбора.** Пять зачарований и
  четыре оберега сохраняют ID, имена и описания, `effects` очищены, числа и триггеры живут в механиках с
  `when.keyValue` по точному русскому имени. Это последняя миграция старого реестра; удаление самих групп
  остаётся общим финальным заходом.
- **`perLevel` — новое общее поле движка.** `resolveFeatureValue` считает `value + perLevel * level`.
  «Ученик Земли» записан как `value: 0, perLevel: 3` (2-й уровень → 6, 10-й → 30), «Ученик Огня» —
  `value: 5, perLevel: 1` (5 + уровень). Смещений «выше 2-го» поле не выражает; это записано в типах,
  чтобы будущие записи не получили двойную базу.
- **Иммунитет ко всем видам урона — `types: ["урон"]`.** `immunityLines` печатает «иммунитет к урону 5»
  вместо перечисления или внутреннего `(урон)`. Мастер Земли использует это для «иммунитета к урону 5».
- **Аколит и Мастер Огня делят `stackingGroup`.** +1 аколита и +5 мастера не складываются: на 10-м уровне
  остаётся ровно +5. Фильтр мастера — все магические способности, аколита — Огонь+Магия.
- **Специализация — подкласс.** `elementalist.specialization` пишется в `subclass`; keyed-наборы 1/2/3/4/5/8/10
  активируются по названию; четыре Аколита без `keyedBy` получили `when.keyValue`. Пустое, неизвестное и
  составное значение не активируют ничего.
- **Пустота выдаёт «Разделенное Чувство Пустоты».** Способность добавлена в
  `SUBCLASS_GRANTED_ABILITIES["Пустота"]` и проверена сборкой всех четырёх специализаций: карточка приходит
  ровно один раз, в ручном выборе её нет. Это была находка ревью: механика ссылалась на способность, а
  билдер её не выдавал.
- **Формы Зелени и аура Мантии — проза.** Таблица животных форм, временная Выносливость, состояния ауры и
  сезонные эффекты лист не хранит; записи дают точное правило и числа, но не подменяют состояние.
- **Великий вирдинг не постоянный иммунитет.** При 5+ Победах игрок выбирает тип урона; это напоминание,
  а не `damageImmunity`.

### Отложено (осознанно)

- Поддержание способностей и уменьшение прибавки эссенции в начале хода — ручное состояние.
- Животные формы Зелени: таблица и выбор формы не разложены на отдельные записи (их нет в скелете).
- Временные иммунитеты, аура Мантии, эффекты Вирдинга, телепорты и выбор типа урона — вручную.
- «Ученик Огня» игнорирует иммунитет цели к огню; модель этого не выражает, это записано в notes.

Тень перенесена целиком: **71 запись скелета = 63 механики + 8 `TEXT_ONLY`** (перки и навыки),

### Решения, принятые при реализации (с ценой ошибки)

- **Коллегии: полное имя в подклассе, короткое в скелете.** Билдер хранит «Коллегия Черного Пепла», а
  keyed-записи размечены «Черный Пепел» / «Едкая Алхимия» / «Маска Арлекина». В `feature-conditions`
  добавлены синонимы значений; `keyValueMatches` и `selectedKeyValues` сравнивают обе формы, панель
  предлагает полные названия и пишет полное имя в `subclass`. Без этого выбор коллегии не активировал бы
  ни одной записи или ломал навыки/способности подкласса.
- **Панель не теряет варианты при рассинхроне подписей.** Для видовых групп подписи `mechanics.choice`

- **Теневая форма — заметка, не постоянный иммунитет.** Иммунитет к порче `5 + уровень`, 1 всплеск,

- **«Уловка» — эпический пул.** Начисляется за отдых, тратится как прозрение и на дополнительные маневры;
  в `runtime.resources` не пишется, как и остальные эпические пулы.
- **Способности из данных не дублируются.** «Внимательное наблюдение» (3), «Ночной дозор» (4), способности
  2/6/9 — из `grantedAbilities`/`abilityChoices`; механики только объясняют запись.
